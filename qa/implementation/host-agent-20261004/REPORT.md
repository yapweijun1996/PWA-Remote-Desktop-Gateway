# Host agent prototype (option A) — real-Mac results, 2026-10-04/05

Target: the owner's Mac (macOS 26.6.2), agent 0.1.0-prototype launched as its own app (`com.rdg.local.agent`, ad-hoc signed) with its own Screen Recording and Accessibility grants. Loopback only; the owner watched. Not integrated with the gateway or PWA, not deployed.

## Input and clipboard (`input-test.mjs`, 15/15 passed, `input-test-results.json`)
Injected only into a throwaway TextEdit file, frontmost app checked before every step:
- plain typing; **Control held 1 s + A** (line start); **Command + A** with 150 ms and 1 s holds; **Command+Space opens Spotlight** and Escape closes it;
- typing Chinese as text; **client → Mac clipboard incl. Chinese and é** and **Command+V paste**; **Mac → client clipboard** on copy;
- holding Command+Control then closing the client releases every key; no modifier is left held at the end.
The same Control and Command tests failed on the built-in Screen Sharing (VNC) path and client → Mac clipboard text never reached the pasteboard (`../mac-input-diagnosis-20261004/REPORT.md`).
Test-method corrections made along the way (not agent faults): TextEdit auto-capitalised the first letter, `pbpaste` needs a UTF-8 locale, and Spotlight is an overlay window rather than the frontmost app.

## Video (loopback, view-only, `measurements.json`, `encoder-experiments.json`)
1470x956 H.264 Main, 29-30 fps, capture-to-decode about 10 ms, agent about 5% of one core. Idle bitrate about 254 kbit/s after moving keyframes from 4 s to 30 s and skipping unchanged frames (was 519). Auto-scroll sits at the 4 Mbit/s target, so the target must adapt to the client's network. No real network, Cloudflare or VNC comparison was measured.

## The encoder-creation stall
After rebuilding and re-granting, the app-launched agent blocked in `VTCompressionSessionCreate`, a synchronous XPC call to `VTEncoderXPCService`, for over a minute while the service sat idle. The same code was fine standalone, inside an unauthorised `.app`, and from a terminal. After a further reset and re-grant it created the encoder in 2.2 s once and then in about 120 ms on every later run (default, encoder-before-capture, software-only, hardware-plain), so the cause was not found and could not be reproduced. The agent now tries low-latency hardware, hardware and software encoders in turn with a 5 s deadline each (software was measured at 29 fps), so a stall degrades instead of hanging.

## Operational lessons
- Every rebuild changes the ad-hoc signature (cdhash); macOS keeps the old grant record and logs `Failed to match existing code requirement`. Reset only the agent's records (`tccutil reset <service> com.rdg.local.agent`) and add the app again.
- Launched from a terminal, the agent inherits the terminal's capture grant (it did once by accident). Always launch with `open`.
- macOS 15+ asks monthly about Screen Recording; the persistent-capture entitlement is not available to an ad-hoc build.

Not verified (S4 and later, on the real Mac): the real Swift agent through the real gateway and Cloudflare Access with the owner watching; scroll feel (the 1:1 default is a first guess to tune on the Mac); hardware decode choice on the owner's browsers, Safari and Windows browsers; Chinese IME; secure-input behaviour; reconnect and bitrate adaptation (S5).

S4 preconditions found by review (the tests above cannot reach them):
1. A bad token mount stops the whole gateway, VNC included, because `RDG_AGENT_ENABLED=true` validates the token file at startup. The mount and environment change is its own approved step (it will trip the deploy script's mounts/ports guard, which must not be routed around), should copy the pattern the deployed compose already uses for the VNC key file, and the new image should be started once beside the running one to check the token's mode, owner and length (never its value) before the running container is replaced. The rollback path must cover a startup refusal.
2. Fast reconnects: "apply picture mode" and recovery run `end()` then `connect()` back to back. `Server.swift` closes synchronously on the same serial queue that accepts connections (encoder stop first, capture stop in a task, then `active` is cleared), so a new connection is queued behind the close and a refusal is unlikely, but capture stop and start may overlap. Change the picture mode twice in a row on the real Mac; if it shows `AGENT_AUTH_FAILED`, add one bounded retry in `AgentRelay.connect()` inside the 10 s deadline (S5).
3. Virtual chords (Remote Copy/Paste buttons) send down, down, up, up with no hold; S1's 15/15 used physical-style holds of at least 150 ms. Press the chord buttons on the real Mac; if they fail, do not patch the PWA blind.
4. This is the first binary WebSocket traffic through Cloudflare (VNC was text only). Record the largest keyframe at Clear and the longest single send over the real Tunnel and Access path; do not assume a limit either way.
Non-blocking for S5 if seen: every `kf` makes the agent resend `config` and `configure()` rebuilds the decoder even when nothing changed; the Accessibility notice is replaced by "View only" at the next blur or resize.

## Stage 2 S4(a) — token mount, candidate image, preflight (nothing deployed)
Approved scope: prepare the compose change and start the new image once beside the running one. Done on throwaway containers and volumes with no network; the running gateway (`rdg-current-mac-pilot-gateway-1`, image `2f011cf8…`) and every other container were verified unchanged before and after, and everything created was removed except the candidate image `rdg-gateway-agent-candidate:s4a` (`928671c06e89`, linux/arm64, built from this branch after `npm run build`: 149 Java tests, 11 runtime JAR digests and 393 pinned OS packages verified).
- `deployment/compose.agent.yaml` is an override; the base compose file is unchanged. A merged render differs from the base only by the four `RDG_AGENT_*` variables and one read-only token bind; every other service setting is identical.
- `agent-startup-check.mjs`, 17/17 (`agent-startup-check.json`): the real token mounted as the override mounts it shows up in the container as a regular file, mode 600, owner 10001:10001, 43 bytes; the candidate starts, reports healthy and never prints the token; the flag-off case starts as today; and the gateway **refuses to start** (exit 1) for a group/other-readable token, a wrong-length token, a non-base64url token, no token mounted, a token path outside `/run/secrets`, and a non-local agent host. Compose refuses to create the container when the token file is missing and creates nothing on the host.
- `topology-check.mjs`, 6/6 (`topology-check.json`): with a stand-in listener bound to 127.0.0.1:5960 (the agent was not running; accept and close, no data), containers on the default bridge and on a user-defined bridge reach `host.docker.internal:5960`, the connection arrives from 127.0.0.1, and a port nobody listens on is refused. So the topology works, and the agent cannot tell the gateway from any other local process: the token is the only barrier.
- S4(b) requirements that follow: deploy from this branch's recorded commit and a clean tree rather than `main` (no merge was approved); an automatic rollback to the previous image and environment when the new gateway is not healthy within 60 s (a bad token looks exactly like that); the token path must exist as a regular file before `compose up`; the mount, port and environment guard is extended deliberately to include the token bind, not bypassed; decide the release number (the web build changes, 1.2.11 or 1.3.0) before building the deployed image.
Not done: nothing is deployed, the gateway keeps running the old image, the agent was not started, no real agent or Cloudflare path was exercised.

## Stage 2 S4(b) — release 1.3.0 deployed with the agent OFF (receipt: `../stage2-s4b-20261005/deployment.json`)
Deployed from branch `codex/host-agent-stage2-20261004`, commit `42d573c` (not from `main`; no merge was approved), image `sha256:0ace2d48…` (linux/arm64), web 1.3.0 build `045b4c19eb27f440`. Only the gateway container was replaced; guacd and the nine other containers were verified unchanged, Access policy and the Tunnel were not touched. The gateway runs as 10001:10001 with a read-only root, publishes only 127.0.0.1:32120, and logged `RDG gateway ready`.
- The agent settings are present and the token is mounted read-only (mode 600, owner 10001:10001, 43 bytes inside the container; the value is not recorded), but `RDG_AGENT_ENABLED=false`, so the route is not registered and the engine selector is not offered. Private environment file changes: `GATEWAY_IMAGE`, `RDG_AGENT_ENABLED`, `RDG_AGENT_TOKEN_SOURCE`.
- The public edge still answers 302 to the Access login. That is informational; it is not a check of the owner's authenticated path.
- **Attempt 1 was rolled back automatically.** It replaced the gateway at 13:25:22, the new gateway was healthy at 13:25:53, and one second later the script rolled back to the previous image and a byte-identical environment file (healthy again at 13:26:25). Cause, reproduced offline against the live environment but not read from a receipt (none was written, the process was probably interrupted by a second invocation): the script compared two environment objects by key order, which cannot match once the agent variables sort into the middle. Fixed in `42d573c` (order-insensitive comparison, failure written before the slow rollback, separate backup names, proof that attempt 1's rollback restored the file). Attempt 2 passed all checks. The attempt-1 and attempt-2 backups of the environment file are kept.
- The rollback path was therefore exercised once on the real deployment.
Not verified: nothing authenticated. The script cannot call the gateway through Access, so that `backends` is `["vnc"]`, that the selector is hidden and that a VNC session works on 1.3.0 are for the owner to confirm in the PWA; (c) does not start before that. No new vulnerability scan of the 1.3.0 image was run.
